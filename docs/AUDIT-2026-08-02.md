# Audit — 2026-08-02

Read-only audit against production (`cue-manav-prod`, `/workspace/data/db/assistant.db`) and
the `cue/handoff-bundle` working tree. No code was changed.

Every claim below is either (a) backed by a production query or log line quoted inline, or
(b) explicitly marked **unverified**. Where a code-level suspicion is contradicted by
production data, that is said out loud rather than dropped.

**Data hygiene:** all production reads were counts, distributions and Cue-authored reason
strings. No message bodies, subjects, addresses or contact details were read or recorded.

**Revision 2 — 2026-08-02, after independent verification.** Two claims were wrong and are
corrected in place rather than deleted:

- **§1.1's root cause was wrong.** I said `maxTokens: 16000`; the cause is the **20-second
  send budget** against a 61-second reasoning call. Confirmed by direct model probe and by
  driving the real scorer over IPC. Acting on my original text would have changed a config
  value and left filing broken. The `maxTokens` divergence is real but not causal.
- **§2.2 is retracted.** `task_runs` is a legacy table nothing reads; the 11 stale rows have
  no user-visible consequence.

Both errors have the same shape, and it is the shape this audit was commissioned to hunt: I
treated an **absence** — a missing usage row, an unread table — as evidence for a specific
cause. Absence is exactly the evidence that cannot carry that weight. Sections §1.2–§1.5,
§2.1, §3 and §4 were checked against a consumer or a live log line and stand as written.

## If you only fix five things

1. **The sidechain send budget** — one bug, two dead features (work-item filing AND contact
   memory). Both time out mid-reasoning and report the abort as an empty answer. §1.1
2. **Contact-memory extraction has four independent silent-success bugs**, and the alarm
   built to catch them can fire at most once per process. §1.2 *(cursor fix landed)*
3. **Graph extraction's checkpoint advances past messages it never read** — ~80% of jobs are
   no-ops that log `"Graph extraction job complete"`. §1.3 *(fix landed)*
4. **Arrivals → work items has no volume brake**: 253 of 321 arrivals in 20 hours became work
   items; 306 of 379 work items are parked and 318 have never run. §2.1
5. **Every hard-coded LLM timeout in the codebase is sized for a non-reasoning model.**
   Filing (20s) and contact extraction (12s) are two instances of one class. §1.1c

## 1. Runs-but-produces-nothing

### 1.1 — The sidechain send budget: filing and contact memory are the SAME bug ★ top finding

**Consequence:** 72 work items unfiled and growing; `contact_memory` has 0 rows after 688
completed extraction jobs. Two of the product's headline "Cue learns / Cue organises"
promises are both off, for one reason.

**Production proof — filing:**

```
sqlite> select coalesce(auto_filed_by,'NULL'), count(*) from work_items group by 1;
NULL|319   cue|3   user_unfiled|57

sqlite> select count(*) from work_items
        where project_id is null and status='queued'
          and coalesce(auto_filed_by,'')!='user_unfiled' and auto_file_confidence is null;
72
```

Daemon log, `/workspace/data/logs/assistant-2026-08-02.log`, every 5 minutes without
exception since the last restart:

```
[14:50:31.761] WARN [work-item-auto-file] auto-file scored nothing usable from the model's reply
    items: 20
    replyChars: 0
[14:50:31.761] INFO [work-item-auto-file] auto-file heartbeat
    ticks: 12   sweeps: 12   outcome: "scorer_miss"   candidates: 68   degraded: true
```

The sweep is healthy, reaches the scorer, sends 20 items, and gets **zero characters back**.

### The cause: the send budget, not the config

> **Corrected 2026-08-02 after independent verification.** My original reading — that
> `maxTokens: 16000` was breaking the call — was wrong, and wrong in a way that would have
> cost someone a morning. It is preserved below under "What I got wrong" because the
> reasoning error is the reusable part.

`AUTO_FILE_TIMEOUT_MS = 20_000` (`work-item-auto-file.ts:76`). Replaying the owner's **real**
filing batch — real titles, real project briefs — cost **3,147 completion tokens, 2,242 of
them reasoning, and 61 seconds**. The scorer is killed at 20s, every time, and has been since
real captured work became ambiguous enough to make a reasoning model deliberate. Contact
extraction has the identical bug against a 12-second budget.

The constant was sized against synthetic batches, which answer in ~8 seconds. That is why
the bug is invisible in tests and total in production: **the input that makes filing worth
doing is the input that makes it time out.**

Verified directly, from the prod machine:
- The configured flash model probed at `max_tokens` 16000, 8192 and 1024 → `finish_reason:
  "stop"`, valid JSON, every time. `maxTokens` is not the cause.
- The real scorer driven through the daemon's IPC socket (`classifyPreviewWorkItems`, 20
  synthetic titles) → 20 valid suggestions in **13.5s**. Same call site, same resolved
  `maxTokens`, same code path. Under the budget, so it passes.

**Why it presents as an empty answer rather than an error** — and why I wrongly ruled a
timeout out. `runBtwSidechain` accumulates only `text_delta` events into `collectedText`
(`btw-sidechain.ts:100-104`). A reasoning model emits reasoning first, so at the 20s abort
`collectedText` is still `""`. The abort surfaces as a resolved call with empty text rather
than a throw, so the `catch` branch — `"auto-file flash scoring failed"`, the line that would
have named a timeout — never runs. Instead the sweep reports
`"scored nothing usable from the model's reply"`, which asserts the model answered. It did
not; it was interrupted mid-thought.

**Fix:** raise both budgets past the real reasoning cost, and make the abort legible —
`runBtwSidechain` already computes `hadTextDeltas` and returns `response`;
`work-item-auto-file.ts:258` logs neither, and neither distinguishes "the model declined" from
"we hung up on it".

### What I got wrong, and why it matters for the next reader

I claimed the scorer "never reaches the model", on the strength of `llm_usage_events` having
no row at any sweep timestamp:

```
sqlite> select time(created_at/1000,'unixepoch'), call_site, input_tokens, output_tokens
        from llm_usage_events where created_at > (strftime('%s','now')-5400)*1000 order by 1 desc;
14:53:47|memoryExtraction|6972|367
14:48:15|replySuggestion|319|15
14:48:11|conversationTitle|195|123     <- a real conversation title, ~200 input tokens
14:45:51|heartbeatAgent|115152|2905
...                                      (nothing at 14:45:31 / 14:50:31 / 14:55:31)
```

**That absence is real but it does not discriminate.** No usage row is written for a call
that never completes, so "no row at the sweep timestamp" is equally consistent with
"never emitted" and with "aborted mid-flight". I read a silence as a specific cause — which
is the exact error this whole audit is about. Worth noting that the ambiguity is not only in
my reasoning: the telemetry genuinely cannot tell those two apart, and a killed call leaving
no trace at all is its own gap.

**What does discriminate is the timing**, and it was in the log I had already pulled. The
warnings land at a dead-constant ~20.000s after each 5-minute tick:

```
14:45:31.783   14:50:31.761   14:55:31.764   15:00:31.766
```

A request that was never emitted fails instantly. A request killed by a fixed timeout lands
at a fixed offset. I read those timestamps as evidence the call was *instantaneous* — I was
differencing consecutive warnings (≈299.98s apart) instead of measuring each one against its
own tick, so a constant 20s cost cancelled itself out and looked like zero.

**The `maxTokens` divergence I found is real, and not the cause.** Recording it because it is
still true and still worth tidying: three callers use `runBtwSidechain` at the
`conversationTitle` call site, and the two broken ones pass a `maxTokens` the working one
does not.

| Caller | File | `maxTokens` passed |
|---|---|---|
| Conversation titles | `assistant/src/memory/conversation-title-service.ts:203-211` | *(omitted → sidechain default 1024)* |
| Work-item auto-file | `assistant/src/work-items/work-item-auto-file.ts:237-247` | `resolveCallSiteConfig(...)` → **16000** |
| Contact memory extract | `assistant/src/contacts/contact-memory-extract-job.ts:529-543` | `resolveCallSiteConfig(...)` → **16000** |

In prod `llm.callSites.conversationTitle = {"profile":"deepseek-v4-flash"}`; that profile sets
provider/model/thinking but **no `maxTokens`**, so `resolveCallSiteConfig` layers
`llm.default`'s 16000 underneath (`llm-resolver.ts:176`). It resembled the previously-recorded
"maxTokens above the open-weight cap" outage closely enough that I stopped looking — a prior
that fit the shape and outran the evidence. The model accepts all three values.

### 1.1c — The timeout constants are a class, not two instances

Filing at 20s and contact extraction at 12s are the two that happen to have been caught.
Both were sized against non-reasoning behaviour, and the prod brain is a reasoning model
whose deliberation scales with input ambiguity — so every hard-coded `timeoutMs` on a
sidechain that handles real user data is suspect on the same grounds. The failure mode is
uniform and silent: the abort resolves as empty text, the caller reads empty as "no result",
and the feature reports a clean nothing.

Worth a single sweep of every `timeoutMs`/`*_TIMEOUT_MS` passed to `runBtwSidechain` or
`provider.sendMessage`, checked against a *real* payload rather than a synthetic one. I did
not do this sweep — see §5.

### 1.2 — Contact memory: four silent-success bugs stacked, and a one-shot alarm

**Consequence:** `contact_memory` = 0 rows. `contacts` = 76. `contact_relationship` = 2.
The People dossier's "what Cue remembers" is permanently empty and
`getContactMemoryHealth` reports `degraded: false`.

Today's sweep, verbatim:

```
[12:30:10.199] INFO [contact-memory-extract] contact-memory sweep finished
    provisioned: 74   candidates: 74   examined: 8   saved: 0   alreadyRead: 0
    outcome: "barren"
```

Beyond §1.1's empty reply, four independent defects each guarantee a zero:

1. **The job path can never identify a contact.**
   `contact-memory-extract-job.ts:589-596` bails on `identifyConversationContact`, which
   (lines 136-181) resolves only via `external_conversation_bindings` or
   `assistant_inbox_conversation_state`. A local/desktop conversation has neither → `null`
   for every job. The worker then logs the outcome at **debug** with no `savedCount`
   (`memory/jobs-worker.ts:568-572`), so `extracted/0` and `extracted/3` are byte-identical
   in the log — and both invisible at prod's `info` floor. This is the 688/0.

2. **The alarm fires at most once, ever.**
   `contact-memory-extract-job.ts:434` — `if (health.consecutiveUnidentified === UNIDENTIFIED_CONVERSATION_WARN_AT)`.
   `===`, not `>=`. It warns on job #20 and stays silent for the next 668. `health` is
   in-memory, so a restart resets the streak to 0. The correctly-written sibling is
   `arrivals/arrival-comprehension.ts:773`, which uses `>=`.

3. **A broken parser resets the degradation streak.**
   `parseExtractionResponse` (lines 250-259) returns `[]` on *every* failure — no array
   match, `JSON.parse` throw, non-array. Line 546 then returns `{ saved: 0 }`, and
   `recordConversationRun` (423-426) counts that as a **success**: it increments
   `conversationsIdentified` and zeroes `consecutiveUnidentified`. A permanently broken
   parser therefore keeps `degraded: false` forever.

4. **The cursor advances on an unparseable reply.** Line 691-694 sets the correspondence
   checkpoint "whatever it yielded". One malformed reply permanently burns that contact's
   correspondence — never re-read. **Fixed 2026-08-02**: an empty reply now leaves the cursor
   alone. This one compounded viciously with §1.1 — every timed-out extraction was silently
   marking mail as read-and-understood, so raising the timeout alone would not have recovered
   the correspondence already burned.

Note that this job's own send budget is **12 seconds** (`EXTRACTION_TIMEOUT_MS`) against
transcript-sized input — the same §1.1 bug, tighter. Contact memory needs both fixes: the
timeout to get an answer at all, and the four defects above so a zero is never again
reported as a success.

Also, the sweep's own health accounting cannot see its likeliest failure: outcomes other
than `extracted` are `continue`d before `examined++` (lines 779-786), so if
`listCorrespondenceFor` matched nothing for everybody, `examined` stays 0,
`consecutiveUnproductiveSweeps` never increments (455-456), and the detector at line 407 can
never fire. Today's `examined: 8` against `candidates: 74` is consistent with most
candidates already failing that way.

### 1.3 — Graph extraction: the checkpoint skips past messages it never read

**Consequence:** ~80% of graph-extraction jobs write nothing and log success. Graph memory
still grows (111 nodes today), so this is a large partial loss, not a total one — the tail
of every conversation is the part that goes missing.

Production, today's log:

```
"No transcript found on disk, skipping extraction"   190 occurrences
"Graph extraction job complete"                      237 occurrences
```
(2026-08-01: 116 / 138.) The completion line carries `nodesCreated: 0, edgesCreated: 0,
triggersCreated: 0` and is logged at `info` on the skip path — a success line on a path that
wrote zero rows.

**Fixed 2026-08-02**: the checkpoint now records the newest message actually read rather than
`MAX(created_at)`. The two aggravating factors below were not part of that fix.

Root cause: `memory/graph/extraction.ts:1198` returns
`lastProcessedTimestamp: conversationTimestamp`, and `conversationTimestamp` (1043-1047)
falls through to `resolveConversationTimestamp` (1206-1218) = `MAX(messages.created_at)` for
the **whole conversation**, ignoring both `afterTimestamp` and what was actually in the
transcript sent to the model. `extraction-job.ts:55-57` writes that straight into the
checkpoint under a comment claiming it uses "the newest message actually processed".

Every conversation gets ≥2 jobs — a debounced one (`memory/indexer.ts:235`) and an
end-of-conversation full pass (`daemon/conversation-lifecycle.ts:175`). After the first, the
checkpoint already sits at the newest message, so the "full transcript" pass always finds
zero new messages. Messages that arrive *during* an LLM call are marked processed without
ever being read.

Two aggravating factors in the same file:
- `loadTranscriptFromDisk` (1273-1276) resolves the directory with `getConversationDirPath`
  (canonical only) while every **writer** goes through `ensureConversationDirPath` →
  `getResolvedConversationDirPath`, which falls back to the legacy `<id>_<ISO>` directory.
  A bare `catch { return null }` at 1306-1308 makes ENOENT indistinguishable from "no
  messages".
- Line 1005-1007: `if (transcript.trim().length < 100) return emptyResult;` — an early
  return with **no log at any level**, counted as a completed run.

### 1.4 — `memory_v2_injection_events` has a writer that production never reaches

`memory_v2_injection_events` = **0 rows**, while memory v2 is enabled and active
(`memory_v2_activation_logs` = 417, modes `context-load` 350 / `per-turn` 67).

The only runtime writer is `recordInjectionEvents`, called from
`memory/v2/injection.ts:639` — which lives inside `injectViaRouter`. Prod never runs router
mode: `memory_v2_router_timing` (an unconditional `log.info` at injection.ts:623) appears
**zero times** in today's log, as does the saturated-index bypass line at 575.

`config/schemas/memory-v2.ts:349` documents that tier-2 page ranking is the time-decayed sum
computed on read *from this table*. With it empty, every page scores 0 and tier 2 is inert.
Prod has no `tier2_size` configured, so nothing user-visible is broken today — but the
ranking signal the design depends on has never been collected, and the table's emptiness is
indistinguishable from "nothing has been injected yet".

**Rank: low urgency, high surprise.** Do not spend tomorrow morning on it; do not ship a
tier-2 feature believing the data exists.

### 2.1 — The unfiled/parked pile is what a new user opens onto ★


The arrival→work-item pipe created 253 items in twenty hours. 306 items are parked, 318
have never run, and 346 have never been assessed. Filing (§1.1) is off, so the pile does not
sort itself. **This is the first screen an alpha user sees**, and it currently reads as a
backlog Cue generated and then abandoned.

The relevance gate is not the culprit and does not need re-litigating — it is doing real
work:

```
decided_by | rule_id            | disposition | n
rule       | list_mail          | filed       | 85
rule       | direct_human       | surfaced    | 43
rule       | bulk_sender_address| filed       | 26
fallback   | (null)             | surfaced    | 156
model      | (null)             | filed/surf  |  5
floor      | known_contact      | surfaced    |  2
```

Two honest observations:
- **The model judge decided 5 of 321.** 112 fallbacks are `"not a message"` (calendar, by
  design) and 44 are the *retrofit* path's `"could not tell from what it still has"`
  (`arrival-retrofit.ts:491`) — backfill over rows whose headers are gone. So the live gate
  is mostly rules, and that is defensible; but a rule-only gate is why 253 items landed.
- **The safety floor fired twice, both times `known_contact`, both for commercial
  newsletter senders** that had been auto-provisioned into the contact book. The floor is
  working; the contact book is polluted, so it protects newsletters. (`contact-retirement`
  retired 27 of 74 auto-provisioned contacts today, which is the same symptom.)

### 2.3 — `⌘K` in the browser (diagnosed only; another agent is fixing it)

Root cause: `apps/web/src/domains/chat/hooks/use-chat-layout-shortcuts.ts:81` routes `⌘K`
through `shouldHandleShortcut`, which returns `false` when `document.activeElement` is an
`INPUT`/`TEXTAREA`/`SELECT`/contenteditable (lines 28-31). The chat composer is a `<textarea>`
that auto-focuses and refocuses aggressively (`use-composer-keyboard.ts:44-72`,
`chat-composer.tsx:426,445`), so `activeElement` is the composer essentially always. The
listener is on `window` and is correctly mounted in the browser build — the guard, not the
mounting, is the bug.

It looks like a desktop-only feature because on macOS `⌘K` never reaches the renderer at
all: it is a main-process accelerator (`apps/macos/src/main/commands.ts:49`) relayed over
IPC to `chat-layout.tsx:511`. A second owner of the key exists at
`use-command-palette.ts:202`, which handled `⌘K` unconditionally as *close*.

**The working tree already contains an uncommitted fix** (`isPaletteOpener()` at
`use-chat-layout-shortcuts.ts:55-69`, plus scoping the close handler to the standalone
Electron window). Worth confirming the fixing agent is not about to redo it.

### 2.4 — Filing service (PKB) is disabled, by design, and says so once

`assistant/src/filing/filing-service.ts:120-126`: `start()` returns immediately when
`memory.v2.enabled` is true, logging `"Filing service disabled — memory v2 is active"` once
at boot. Prod has `memory.v2.enabled = true`. This is intentional, but note that `filingAgent`
and `compactionAgent` call sites appear in config and in `call-site-defaults.ts:69` while
never being reachable — and `filing` in the work-item sense (§1.1) is an entirely different
subsystem with the same name. If anyone greps "filing" tomorrow they will read the wrong
file.

firing** — production contradicts the code reading:
